## ⚠️ Текущие замечания, риски и рекомендации (Инфраструктура и деплой Convefy)

### 1. Инфраструктура и выживаемость хоста (1 vCPU / 2 ГБ RAM)
* **Перезагрузка ядра ОС:**  
  В выводе motd зафиксировано предупреждение `*** System restart required ***` и 64 неустановленных обновления. Требуется провести плановую перезагрузку сервера (`sudo reboot`) в ночное окно с минимальным трафиком для применения обновлений безопасности ядра Linux 6.8.
* **Фиксация Swap после перезагрузки:**  
  Необходимо убедиться, что swapfile зафиксирован в `/etc/fstab`, а параметр `vm.swappiness=10` внесён в `/etc/sysctl.conf`. Без этого после перезагрузки swap может не подняться автоматически.
* **Резервные копии:**  
  В панели хостинга статус *«Резервные копии: Нет»*. Рекомендуется включить регулярные снапшоты диска на уровне хостинга.

### 2. Риск падения прав доступа к `tmp_files` при перевыкатке
* **Проблема:**  
  Каталог `/var/www/convert/tmp_files` примонтирован в контейнеры как bind mount с правами `10001:www-data 775`. Если папка будет удалена или проект развернётся на чистом хосте, Docker Compose создаст её автоматически с владельцем `root:root (755)`. В этом случае контейнер с UID `10001` упадет с системной ошибкой Django `converter.E001`.
* **Решение:**  
  В скрипт `backend/deploy.sh` перед `docker compose up` добавить превентивное создание директории:
  ```bash
  mkdir -p /var/www/convert/tmp_files
  chown -R 10001:www-data /var/www/convert/tmp_files 2>/dev/null || true
  chmod 775 /var/www/convert/tmp_files 2>/dev/null || true
  ```

### 3. Нагрузка на CPU во время деплоя (CI/CD)
* **Проблема:**  
  Команда `docker compose build web` выполняется прямо на сервере. На 1 vCPU компиляция C-библиотек и `pip install` нагружают процессор на 100% на 2–3 минуты, вызывая лаги у активных пользователей.
* **Решение:**  
  В планах развития перенести сборку Docker-образов в **GitHub Container Registry (GHCR)** в GitHub Actions, оставив на сервере только `docker compose pull`.

### 4. Страховка от переполнения диска при сбое Celery Beat
* **Проблема:**  
  Файлы удаляются планировщиком Celery Beat раз в 5 минут. Если сервис `celery_beat` зависнет или аварийно остановится, файлы начнут бесконтрольно накапливаться на 100 ГБ диске.
* **Решение:**  
  Добавить на уровне системного cron хоста (`/etc/cron.hourly/clean-tmp`) резервное удаление старых файлов:
  ```bash
  find /var/www/convert/tmp_files -type f -mmin +120 -delete
  ```

### 5. Безопасность и отзыв токенов
* **GitHub PAT:**  
  Токен `ghp_...`, использовавшийся при настройке, после завершения работ следует отозвать (Revoke в настройках GitHub) или установить ему короткий срок жизни.
* **SSH-доступ:**  
  Убедиться, что для пользователя `root` в `/etc/ssh/sshd_config` разрешён вход **только по SSH-ключам** (`PermitRootLogin prohibit-password`).
