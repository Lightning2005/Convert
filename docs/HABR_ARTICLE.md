# Как и зачем я написал свой open-source «Конверт» на Django, Celery и React

Всё началось с банальной студенческой задачи: мне понадобилось собрать пачку фотографий в один аккуратный PDF-документ для портфолио по учёбе. 

Я воспользовался парой готовых онлайн-конвертеров из поиска, решил задачу и… задумался. А как вообще устроены такие сервисы под капотом? Что происходит с файлом после нажатия кнопки «Загрузить»? Как масштабировать обработку тяжелой графики, чтобы сервер не ложился? И главное — вопрос конфиденциальности: когда загружаешь в сторонний облачный сервис учебные документы, сканы или бланки, не всегда понятно, сколько они там хранятся и куда уходят.

Мне стало искренне интересно попробовать написать такой сервис самому — с нуля, для себя, с открытым исходным кодом и понятной логикой удаления файлов.

Около месяца урывками по вечерам я писал первые версии по гайдам и документации. Потом навалилась учёба, проект отправился «в стол» на пару месяцев. Вернулся к нему я уже с новым инструментом — ИИ-агентами, которые взяли на себя львиную долю рутины: помогли настроить CI/CD пайплайны, серверный пререндеринг статики (SSG) и боевую конфигурацию сервера. 

Сегодня **«Конверт»** ([convefy.ru](https://convefy.ru)) — это рабочий сервис с 25 инструментами конвертации, открытым исходным кодом ([репозиторий на GitHub](https://github.com/Lightning2005/Convert)) и архитектурой на **Django 6 + Celery + React 19**, который стабильно живёт на крошечной VDS за 274 рубля в месяц.

В этой статье я расскажу, как устроена система, с какими неочевидными граблями обработки графики я столкнулся и как запустить такой проект без раздувания бюджета на инфраструктуру.

## 1. Концепция: открытость и «Zero-Storage»

С самого начала я определил для себя несколько правил:

1. **Никакой базы данных пользователей.** В `converter/models.py` буквально нет пользовательских моделей. Мы не собираем email, не заводим профили и не ведём логи того, кто и что загружал. `db.sqlite3` используется только под внутренние системные таблицы самого Django.
2. **Гарантированное удаление (TTL).** Все исходные и сконвертированные файлы хранятся во временном томе ровно 55 минут, после чего фоновая задача Celery Beat безвозвратно вычищает их по расписанию раз в 5 минут.
3. **Чистый и предсказуемый интерфейс.** Без обязательной регистрации, ограничений на скачивание и с возможностью пакетной обработки до 40 файлов за раз.

## 2. Архитектура бэкенда: почему Celery + Redis

Первая мысль при создании пет-проекта: взять Django/FastAPI, принять файл в `views.py`, сконвертировать через `Pillow` в синхронном потоке и вернуть `FileResponse`. 

На локальной машине с одной картинкой это работает мгновенно. Но если пользователь отправляет 20 «тяжёлых» снимков или многостраничный PDF, синхронный воркер Gunicorn зависает на десятки секунд. Пара таких одновременных запросов — и бэкенд перестаёт отвечать на любые другие вызовы.

Поэтому обработка вынесена в фоновые очереди:

```text
Браузер
  │
  │  POST /api/... (multipart/form-data)
  ▼
Nginx (проксирует /api/ на 127.0.0.1:8000)
  │
  ▼
Gunicorn / Django (converter/views.py)
  ├── 1. Проверяет заголовки, типы и лимиты
  ├── 2. Сохраняет файл в изолированный том tmp_files
  ├── 3. Пишет статус 'queued' в Redis (кэш Django)
  └── 4. Ставит задачу в Celery (Redis, брокер) ──► Возвращает 202 Accepted + task_id
                                                            │
Браузер ◄── GET /api/status/<task_id>/ (поллинг) ───────────┘
  │
Celery Worker (converter/tasks.py)
  ├── Запускает стратегию конвертации
  ├── Пишет результат во временный .part-файл
  └── os.replace() в итоговый файл ──► Обновляет статус задачи на SUCCESS
```

### Две важные детали реализации очереди:

#### 1. Двухфазная запись и at-least-once delivery
Celery гарантирует доставку сообщения «не менее одного раза». Если воркер упадёт или перезагрузится контейнер прямо во время записи большого архива, задача выполнится повторно. Если писать сразу в итоговый файл, повторная попытка может прочитать недописанный огрызок.

Поэтому результат всегда пишется во временный файл `.part`, а затем атомарно перемещается через `os.replace`:

```python
# converter/tasks.py
part_path = f"{output_path}.part"
strategy.convert(input_path, part_path, **kwargs)
os.replace(part_path, output_path)
```

Первая строчка любой стратегии — проверка `is_already_done(output_path)`. Если файл с таким UUID уже лежит на диске (воркер успел всё сделать, но упал до отправки сигнала ack), задача сразу возвращает `SUCCESS` без повторной конвертации.

#### 2. Различие PENDING и UNKNOWN
По умолчанию Celery возвращает статус `PENDING` и для задач, которые действительно ждут своей очереди, и для любых случайных или несуществующих ID. 

Фронтенд начинает опрашивать API практически мгновенно после получения ответа. В коротком зазоре между ответом Django и постановкой в очередь воркером клиент успевал получить ложный `PENDING`. Поэтому мы вызываем `mark_task_queued(task_id)`, которая сохраняет метку в Redis **строго до** вызова `apply_async()`.

## 3. Грабли с графикой: чёрные дыры и перевернутые страницы

Конвертация изображений на практике оказалась полна нюансов, с которыми я раньше никогда не сталкивался.

### Грабли №1: Чёрный фон вместо прозрачности
При тестировании конвертации PNG в JPG и PDF я загрузил иконку с прозрачным фоном и на выходе получил изображение на сплошном чёрном квадрате.

Форматы JPEG и стандартный RGB-холст в PDF не поддерживают альфа-канал. Если передать библиотеке Pillow изображение в режиме `RGBA` и сохранить как `RGB`, прозрачные пиксели с нулевой альфой превращаются в `(0, 0, 0)` — то есть в чёрный цвет. 

Ситуация усложняется палитровыми PNG (`mode='P'`), где прозрачность задаётся через палитру. Решение — принудительный композитинг на белый фон:

```python
# converter/strategies.py
img = Image.open(path)

# Если картинка палитровая с прозрачностью, приводим к RGBA
if img.mode == 'P' and 'transparency' in img.info:
    img = img.convert('RGBA')

# Накладываем альфа-канал на белую подложку
if img.mode in ('RGBA', 'LA'):
    background = Image.new('RGB', img.size, (255, 255, 255))
    background.paste(img, mask=img.split()[-1])
    img = background
elif img.mode != 'RGB':
    img = img.convert('RGB')
```

### Грабли №2: Снимки с айфона упорно ложатся на бок
Камера iPhone по умолчанию сохраняет фотографии в формате HEIC и оставляет физическую матрицу сенсора в горизонтальной ориентации, записывая правильный угол поворота (тег Orientation) в метаданные EXIF.

Если просто декодировать HEIC и вставить в PDF, вертикальный документ оказывается повёрнутым на 90 градусов. Чтобы этого избежать, мы обязательно прогоняем изображение через встроенный в Pillow метод `ImageOps.exif_transpose()`:

```python
from PIL import Image, ImageOps

img = Image.open(path)
# Читает тег ориентации EXIF и физически поворачивает матрицу пикселей
img = ImageOps.exif_transpose(img)
```

### Грабли №3: Формат листа и центрирование в ReportLab
При сборке PDF через ReportLab нужно вручную рассчитывать геометрию листа A4. Чтобы документ выглядел аккуратно, изображение пропорционально масштабируется и центрируется, а в свойствах документа явно задаётся заголовок, иначе просмотрщик в браузере показывает некрасивый дефолтный заголовок «untitled»:

```python
pdf_canvas = canvas.Canvas(output_path)
pdf_canvas.setTitle(kwargs.get('document_title') or 'converted_images')
page_width, page_height = A4  # 595.27 x 841.89 pt

# Масштабирование с сохранением пропорций
ratio = min(page_width / img_w, page_height / img_h)
new_w, new_h = img_w * ratio, img_h * ratio

# Центрирование на листе
x = (page_width - new_w) / 2
y = (page_height - new_h) / 2

pdf_canvas.setPageSize((page_width, page_height))
pdf_canvas.drawImage(ImageReader(img), x, y, width=new_w, height=new_h)
pdf_canvas.showPage()
pdf_canvas.save()
```

## 4. Как уложить продакшен в 2 ГБ RAM (VDS за 274 ₽/мес)

Сервер проекта крутится на скромной виртуальной машине: **1 vCPU, 2 ГБ RAM, 100 ГБ диска на Ubuntu 24.04**. 

Там одновременно запущены Nginx, Gunicorn с Django, Redis, Celery Worker и Celery Beat. Памяти немного, поэтому защита от падений по OOM (Out Of Memory) была продумана заранее, ещё до первого релиза.

### 1. Защита от декомпрессионных бомб (Pixel Flood)
Изображение 10000×10000 px в формате PNG со сплошной заливкой может весить на диске всего 300 КБ благодаря сжатию. Но когда бэкенд распаковывает его в оперативную память, оно превращается в ~300 МБ сырого битмапа. Пять таких файлов — и двухгигабайтный сервер уходит в OOM.

Мы проверяем разрешение изображения **до** постановки в очередь задач, считывая только метаданные из заголовка файла:

```python
# converter/views.py
MAX_IMAGE_PIXELS = 50_000_000  # 50 Мегапикселей

with Image.open(uploaded_file) as img:
    w, h = img.size
    if w * h > MAX_IMAGE_PIXELS:
        return Response(
            {"error": "Изображение слишком велико (превышен лимит 50 Мпикс)."},
            status=status.HTTP_400_BAD_REQUEST
        )
```

### 2. Чанкинг страниц при рендеринге PDF
При конвертации PDF в изображения мы используем PyMuPDF (`fitz`) с плотностью **200 DPI** — это даёт чёткий, легко читаемый текст на сканах.

Но если пользователь загрузит документ на 100 страниц и мы попытаемся отрендерить их все в память разом, пиковое потребление памяти превысит 3 ГБ. Поэтому рендеринг разбит на пачки по 10 страниц (`PAGE_CHUNK = 10`), которые сразу упаковываются в выходной ZIP-архив с освобождением памяти:

```python
# converter/strategies.py
PAGE_CHUNK = 10

with fitz.open(input_path) as doc:
    page_count = len(doc)
    with zipfile.ZipFile(output_path, 'w', compression=zipfile.ZIP_DEFLATED) as zip_file:
        for first_page in range(0, page_count, PAGE_CHUNK):
            last_page = min(first_page + PAGE_CHUNK, page_count)
            for page_num in range(first_page, last_page):
                page = doc[page_num]
                pix = page.get_pixmap(dpi=200)
                zip_file.writestr(f"page_{page_num + 1}.jpg", pix.tobytes("jpg"))
                pix = None  # Освобождаем память под сборщик мусора
```

### 3. Запас 1 МБ в Nginx
В конфиге Nginx задан лимит `client_max_body_size 51M`, а в валидаторе Django — ровно 50 МБ. Этот запас в 1 МБ нужен для того, чтобы multipart-заголовки формы не отсекались на уровне Nginx «сухой» ошибкой 413, а доходили до приложения, позволяя вернуть понятное сообщение на русском языке.

## 5. Фронтенд: Smart Intent Routing

Фронтенд собран на **React 19 + Vite 8 + Tailwind CSS v4**. Для удобной сортировки страниц перед склейкой в PDF подключена библиотека `@dnd-kit`.

Интересная деталь UX — **Smart Intent Routing**. Часто бывает так: человек переходит из поисковика на страницу «Конвертировать JPG в PDF» и машинально сбрасывает в окно загрузки фотографии HEIC с телефона.

Вместо того чтобы выдавать сухое сообщение «Неверный формат», фронтенд проверяет расширения и MIME-типы файлов на клиенте и, если находит совпадение среди других инструментов, показывает ненавязчивую плашку:

> *«Вы добавили файлы HEIC. Переключиться на инструмент **HEIC в PDF**? Файлы сохранятся!»*

В один клик происходит переход на нужный маршрут, а все выбранные файлы и сгенерированные превью остаются на месте без повторной загрузки.

## 6. SEO без Next.js: Пререндеринг на Node.js

В проекте 25 конвертеров (JPG в PDF, PNG в WebP, PDF в JPG, ICO в PNG и др.). Каждому инструменту нужна своя посадочная страница, мета-теги, FAQ и микроразметка Schema.org.

Классический SPA на чистом React индексируется поисковыми роботами со скрипом, так как изначально отдаёт пустой `<div id="root"></div>`. Тащить ради этого полноразмерный **Next.js** с его постоянным Node.js-сервером в продакшене я не хотел — для VDS с 2 ГБ памяти это лишняя постоянная нагрузка.

Вместо этого мы написали простой билд-скрипт пререндеринга (`frontend/scripts/prerender.mjs`):

```text
npm run build
  ├── 1. Vite собирает клиентский бандл
  ├── 2. Vite собирает серверную точку входа (entry-server.js)
  └── 3. Node.js запускает prerender.mjs:
           ├── Перебирает все 28 маршрутов
           ├── Рендерит дерево React в статичный HTML (renderToString)
           ├── Подставляет title, description, canonical и OpenGraph
           ├── Внедряет валидный JSON-LD (SoftwareApplication, FAQPage)
           └── Записывает готовые 28 .html файлов в папку dist/
```

В результате Nginx раздаёт готовый плоский HTML за считанные миллисекунды, а в браузере пользователя происходит обычная гидратация React.

Чтобы метаразметка никогда не расходилась с реальным текстом страницы, в CI добавлен валидатор `verify-dist.mjs`, который проверяет сгенерированный `dist/` перед деплоем и гарантирует соответствие Schema.org.

## 7. Где помогли ИИ-агенты

После двух месяцев простоя именно связка с современными ИИ-агентами помогла мне быстро довести проект до финала. В чём они проявили себя лучше всего:

* **CI/CD и деплой:** составление пайплайнов GitHub Actions, написание скрипта проверки секретов `check_secrets.py`, чтобы случайно не запушить чувствительные переменные, и генерация конфигов Nginx / Docker Compose.
* **SEO и пререндеринг:** архитектура скрипта `prerender.mjs` с подстановкой JSON-LD и верификатора `verify-dist.mjs`.
* **Тесты и контракты:** покрытие бэкенда тестами на граничные случаи (битые файлы, некорректные форматы, тайм-ауты).

Для студента такой инструмент работает как опытный ментор: ты продумываешь логику и архитектуру, а рутинную обвязку и валидаторы делегируешь ИИ.
